# Direct USB printing for the PM2411BT — verified findings, spec, integration

**For users:** plug the printer in. On Windows nothing else is needed; on
Linux install the udev rule (end of this page). It appears as
`PM2411BT (USB direct, serial ...)` in `ibp-print-diag` and is tried before
every print queue. `IBP_PRINTING_DIRECT=0` turns the direct path off. What
the volunteer sees on cover open / paper out, and how fallback works, is in
the README's *Direct USB printing* section and under *Integration* below.

Goal: print 4x6 labels and read status by talking to the printer directly over
USB, with identical behaviour on Linux (dev) and Windows (IBP shipping PCs), no
vendor driver, no CUPS, no Windows print queue. The existing GDI/CUPS backends
stay as a fallback.

## Verified on real hardware (2026-10-04, Arch laptop, usblp)
- USB 2e3c:5760 (VID = Artery AT32 MCU, shared by many OEM models), iManufacturer
  "PM", iProduct "PM2411BT", serial present. One interface: printer class 7/1
  proto 2 (bidirectional), bulk OUT 0x01, bulk IN 0x82, 64-byte packets.
  1284 ID: `MFG: ;CMD:XPP,XL;MDL:PM2411BT;CLS:PRINTER;DES:PM2411BT;`.
  Identify by 1284 MDL (and/or iProduct), not by VID:PID alone.
- Linux: usblp gives /dev/usb/lpN (root:lp 0660; single open — second open
  EBUSY). Reads work on the same fd; the reader must keep polling through
  empty reads (a reader that stops at the first empty read misses replies).
- The printer is LINE-BUFFERED: nothing is acted on until CR LF. Unknown lines
  are answered `Cmd error:<line>\r\n`. Binary queries without CR LF just sit in
  the buffer (that's why ESC/POS / TSPL binary status queries "didn't answer").
- Queries that work over USB (reply within ~1 s, CR LF terminated):
  - `SSSGETCAP\r\n` -> `SSSGETCAP:OPEN` / `SSSGETCAP:CLOSE` — reliable, changes
    immediately with the cover.
  - `SSSGETPAPER\r\n` -> `SSSGETPAPER:YES` — UNRELIABLE: stayed YES with the roll
    removed (sensor apparently only read when feeding). Log it, never trust it.
- Not supported over USB (answer `Cmd error:`): `SSSGETPRINTING`,
  `SSSGETPAPERCAPACITY`, `ESC !?` (+CRLF). LPGETSTATUS ioctl is always 0x00.
- Unsolicited pushes from the printer (no query needed):
  `SSSGETPRINTING:DOING\r\n` when it starts moving paper and
  `SSSGETPRINTING:DONE\r\n` when finished — for a real print AND for the
  automatic realign it performs every time the cover is closed (~1–6 s, uses no
  label). Also pushes `SSSGETCAP:OPEN/CLOSE` on cover changes (seen queued).
- Print job (copied from the vendor Linux filter for model 100, verified by one
  successful print: single label, correct orientation (top first), black on
  white, all 1–4-dot lines resolved, top/bottom edges within ~1 mm of the cut):
  ```
  \r\n
  SIZE 102 mm,152 mm\r\n REFERENCE 0,0\r\n DIRECTION 0,0\r\n GAP 3.0 mm,0.0 mm\r\n
  SET TEAR ON\r\n OFFSET 0 mm\r\n SPEED 4\r\n CLS\r\n
  BITMAP 0,0,102,1218,4,<payload>\r\nPRINT 1,1\r\n
  ```
  (no spaces before the commands — shown spaced for readability)
  Image 812x1218 dots @203 dpi, 102 bytes/row, MSB-first, dark if grey <= 0xAF,
  bytes INVERTED (0 = black). Payload (mode 4): raster split into 4096-byte
  slices, each LZO1X-1 compressed and prefixed with its compressed length as
  4-byte little-endian; terminated by 4 zero bytes. Reference job builder:
  scratchpad/build_job.py (uses system liblzo2 via ctypes — not available on
  Windows). Uncompressed BITMAP modes are UNTESTED on this model.
- Paper out (roll removed, cover closed, job sent): the printer never pushed
  DOING, never sent an error line, SSSGETPAPER still YES; it stopped accepting
  data part-way (writes hit EAGAIN / did not drain). The partial job stays in
  the printer; it must be power-cycled before reloading paper or it may print
  the leftover / swallow the next job's text as bitmap data. (Test script
  crashed on EAGAIN in its polling loop — handle EAGAIN on writes of queries.)

## Outcome mapping for a direct print (fit into existing PrintError / JobOutcome)
- Device can't be opened / not found / busy, or pre-check fails (cover OPEN,
  or a realign DOING not finished within a short wait) -> PrintError
  (definitely nothing sent; safe to fall back / queue to to-print).
- Write did not fully drain within a timeout (paper out / jam / stuck) ->
  UNCERTAIN, with history "printer stopped accepting data (paper out?); power
  cycle the printer before reloading paper" (a partial job is in the printer).
- Fully written, DOING then DONE within timeout -> COMPLETED.
- Fully written, DOING but no DONE within timeout -> TIMEOUT (not ok).
- Fully written, no DOING within ~10 s -> UNCERTAIN.
- Any query write that hits EAGAIN must not crash; treat as "printer busy".
- Never resend a job automatically after anything but PrintError.

## Proposed module layout (ibp_printing/direct/)
- `transport.py`: `Transport` ABC — `write_all(data, timeout_s) -> int` (bytes
  accepted; never raises on timeout, returns the count), `read_lines(timeout_s)
  -> list[str]` (keeps reading through empty reads), `close()`, plus
  `DirectDevice` dataclass (path, vid_pid, serial, ieee1284 dict, model).
  Implementations: `LinuxUsblpTransport` (/dev/usb/lpN, sysfs ieee1284_id /
  idVendor / idProduct / serial for discovery), `WindowsUsbprintTransport`
  (SetupAPI enumerate GUID_DEVINTERFACE_USBPRINT
  {28d78fad-5a12-11d1-ae5b-0000f803a8c2} via ctypes, CreateFile overlapped,
  IOCTL_USBPRINT_GET_1284_ID for model, ReadFile/WriteFile with wait+CancelIo
  timeouts; reads can otherwise block forever), `FakeTransport` for tests
  (scriptable replies, partial writes, stalls). `discover_direct_devices()`.
- `lzo.py`: LZO1X-1 compressor that works on Windows with no system library —
  pure-Python (or a vetted wheel available for win+linux py3.12), verified by
  round-trip against liblzo2's decompressor in tests when present, and byte-
  compatible with what the printer accepted.
- `tspl.py`: rasterize (fit/rotate/threshold to 812x1218 - originally "reuse
  render.py conventions incl. 95% scale-to-fit"; superseded, see *Image
  placement* below), pack, build job; parse printer lines
  (`SSSGETCAP:*`, `SSSGETPAPER:*`, `SSSGETPRINTING:*`, `Cmd error:*`, other).
- `session.py`: one print = open -> drain/parse queued lines -> pre-check ->
  write job -> watch pushes -> outcome; very verbose structured logging of
  every byte count, line and timing, using ibp_printing.log conventions.

## Linux: device permissions (udev rule)
`/dev/usb/lpN` is `root:lp 0660`, so a normal user gets EACCES (the transport
raises `DeviceUnavailable(reason="permission")` naming the rule below).
Install `packaging/linux/60-ibp-label-printer.rules`, which tags usblp nodes of
USB vendor `2e3c` with `uaccess` (an ACL for the logged-in desktop user only):
```
sudo install -m 0644 packaging/linux/60-ibp-label-printer.rules /etc/udev/rules.d/
sudo udevadm control --reload && sudo udevadm trigger --subsystem-match=usbmisc
getfacl /dev/usb/lp0   # expect a "user:<you>:rw-" line
```
(or replug the printer instead of `trigger`). A manual `setfacl` is lost at the
next replug / power cycle; the rule is not. Adding the user to the `lp` group
also works but needs a re-login and grants every printer. If another program
has the node open, our open fails with EBUSY (`reason="busy"`).

## Integration (implemented)

Modules: `direct/transport.py` (USB I/O), `direct/lzo.py`, `direct/tspl.py`
(raster + job + line parsing), `direct/session.py` (one print, status
probe), `direct/backend.py` (`DirectFirstBackend`), `direct/config.py` (kill
switch).

### Discovery
- `create_backend()` returns `DirectFirstBackend(<GDI or CUPS backend>)`.
  Its `discover()` runs the platform discovery, then
  `discover_direct_devices()`, and merges the result
  (`discovery.merge_direct`). Direct discovery never raises: a failure is
  logged and added to `discovery.errors`; the queues are still returned.
- Every USB printer-class device is listed in `discovery.direct_devices`.
  A device becomes a `PrinterCandidate` (`transport == "direct"`,
  `direct_device` set, name `"<MDL> (USB direct, serial <serial>)"` or the
  path if there is no serial) when its 1284 MDL is supported
  (`models.SUPPORTED_DIRECT_MODELS = {"PM2411BT"}`, case-insensitive) or it
  has the PM2411BT's VID:PID (then it is listed as *not usable* so
  diagnostics can explain it). Other printers are never candidates and never
  receive a byte (not even a status query).
- Usable = present (device node exists) and supported model. On Windows the
  1284 ID is read by opening the device; if that open fails because the device
  is busy, the model is unknown and the direct candidate is not usable for that
  pass (its Windows queue, if any, is).
- Ranking: a direct candidate that is healthy (present, not busy, not known
  to lack permission) ranks before every queue. One with a known problem
  (e.g. no permission on Linux) ranks with the unhealthy queues. Queue ranking
  is unchanged.
- A queue with the same VID:PID as a usable direct candidate (a Windows queue
  for the same printer, named with the `VID:PID` rule) stays a candidate,
  ranked after the direct one, with a reason "probably the same printer as
  ...; used only if direct USB printing definitely did not print".

### Printing and outcome mapping
`api.print_to_first_available` calls `backend.print_to_candidate()` (new
`PrinterBackend` method; the default prints by name, so custom backends keep
working). `print_image(img, "<direct name>")` rediscovers and finds the
device by name. One direct print = open (exclusive) -> `print_label()` ->
close.

| What happened | API result | Fallback to the next candidate? |
|---|---|---|
| Open failed: busy (spooler / other program), permission, unplugged | `DirectPrintError` (`PrintError`), `.reason` = `busy` / `permission` / `not_found` / `error` | yes (nothing sent) |
| Pre-check failed: cover open, no reply, realign never finished, query I/O failed, no job byte accepted, bad image | `DirectPrintError`, `.reason` = `cover_open` / `no_cover_reply` / `realign_busy` / `transport_error` / `job_not_accepted` / `bad_image` | yes (nothing sent) |
| Direct disabled by the kill switch but a direct name was asked for | `DirectPrintError`, `.reason` = `disabled` | yes |
| DOING then DONE | `PrintResult` `COMPLETED` | no (done) |
| Job write stalled part-way (paper out / jam) or the device died mid-job | `UNCERTAIN`, history says "power-cycle it before reloading paper" | **never** |
| Job written, no DOING within 10 s | `UNCERTAIN` | **never** |
| DOING but no DONE within the wait | `TIMEOUT` | **never** |
| Printer answered `Cmd error:` to part of the job | `ERROR` | **never** |

`PrintResult.job_id` is None; `history` starts with the device path/serial
and the open time, followed by the session's timestamped history. The
session's full record (`SessionResult.to_log()`: every line received with its
time, bytes written, timings) is logged at INFO/ERROR.

`track_timeout_s`: direct jobs are always watched (DOING/DONE are pushed by
the printer), so `track_timeout_s=0` still yields COMPLETED/UNCERTAIN/...,
never NOT_TRACKED. The wait for DONE is `max(track_timeout_s, 30 s)`; the 10 s
wait for DOING and the pre-check/write timeouts are fixed
(`SessionTimeouts`). Worst case for one call is roughly 0.5 s drain + ~3 s
queries + 20 s write stall + 10 s DOING, or DOING + `max(track_timeout_s, 30)`.

### Device contention / share mode
- Linux: usblp allows a single open; a second open gets EBUSY ->
  `DeviceUnavailable(reason="busy")` -> `PrintError`.
- Windows: `CreateFileW` with share mode **0 (exclusive)**
  (`transport.USBPRINT_SHARE_MODE`). While we hold the handle, the spooler's
  USB port monitor (which opens the same usbprint interface for each job it
  sends) cannot open it, so it can never interleave another job's bytes into
  ours (the printer would read them as bitmap data). Reads are unaffected:
  they use our own handle; share mode only governs other opens. The cost:
  while anything else holds the device (the spooler printing a queued job to
  it, another program), our open fails with `ERROR_SHARING_VIOLATION` (or
  `ERROR_ACCESS_DENIED`) -> `reason="busy"` -> `PrintError`, so the job falls
  back (or the watcher keeps it in `to-print\`). A spooler job that arrives
  while we print should wait/retry and print after we close (to verify on
  hardware).
- Within one process two threads printing at once behave the same way: the
  second one gets "busy" and falls back.

### Kill switch
`IBP_PRINTING_DIRECT=0|false|no|off` (or `1|true|yes|on`),
`ibp_printing.set_direct_enabled(False|True|None)`, `ibp-print-diag
--no-direct`, or `DirectFirstBackend(..., enabled=False)`. Read on every
discovery and print. When off, discovery skips the direct layer and printing
goes to the platform backend: exactly the old behaviour. The mode and what
decided it are logged by every `configure_logging()` call and when the
backend is created.

### Diagnostics
`ibp-print-diag` starts with a *Direct USB printers* section (mode, every
printer-class device with path, kind, VID:PID, serial, 1284 ID, supported,
present/accessible/busy, errors, candidate reasons and verdict) and a status
probe for supported models: `session.probe_status()` drains pushed lines and
sends only `SSSGETCAP` and `SSSGETPAPER` (plus a bare CR LF if a query was cut
short), so it cannot feed or print a label. `--direct-status` prints only
that (exit 0 when every supported printer is ready: cover CLOSE, no realign
running). `--test-print` uses the direct path when a supported printer is
present.

### Image placement (barcode fidelity)
`tspl.place_on_label`: rotate landscape to portrait; an 812x1218 image is
used dot for dot (the verified `test_job.bin` is reproduced from
`test_label.png` through `rasterize()`); anything else is scaled to **fill**
the label (100 %, aspect kept, centered) with **NEAREST**, then the 0xAF
threshold. The GDI path's 95 % backoff is not used: the verified 812x1218
print had every edge within ~1 mm of the cut, and any non-integer shrink
hurts barcodes.

Study (`tests/test_direct_barcodes.py`, zbar via pyzbar; Code 128
`1Z999AA10123456784` and USPS IMpb GS1-128 `420 78701 92 0559...`, module
widths 2-5 px, sources 1200x1800, 1218x1827, 1624x2436, 1000x1500, 1700x2550,
812x1218, 8 bar phases, simulated dot gain -1/4..+2/4 dot): decoded
NEAREST 100 % 449/512, LANCZOS 100 % (0x80) 416, BOX 100 % 366, LANCZOS 95 %
(0xAF, the old rule) 299; at 95 % every method was worse (NEAREST 358). On
the main case (1200x1800 EasyPost, X = 3-4 px) the old rule decoded 77/96 of
the test's cases and the new one 96/96. Integer ratios (1x, 1.5x, 2x) keep
bar widths exact; 1200x1800 keeps every bar/space within one dot.
Thin (1 px at 300 dpi) lines can disappear with NEAREST; they are below the
printer's resolution anyway (0.68 dot).

### Open questions for the hardware test
- Print a real EasyPost 1200x1800 label at 100 % fill: edges inside the
  label? Barcodes scan (phone / USPS scanner)?
- Windows: does `usbprint.sys` hand out the device to us while a queue exists
  for it, and does a spooler job submitted during a direct print wait and then
  print (no interleaving, no lost job)? Does the spooler keep the device open
  between jobs (would make direct always "busy")?
- Windows: does exclusive open + overlapped ReadFile get the pushed
  `SSSGETPRINTING` lines like usblp does?
- Paper out with the full-size job (~10-30 KB compressed): does the write
  still stall part-way (-> UNCERTAIN with the power-cycle hint), or is the
  whole job buffered (-> UNCERTAIN "never reported printing")?
- Are 30 s (DONE) and 10 s (DOING) the right waits for a long label at
  SPEED 4?
